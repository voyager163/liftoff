## Context

See proposal.md. The released local Azure repair uses an expiring external schema-1 preview bound to CLI version and the combined recipe string `azure-local-layout-v1`. Repair and update share a sealed recoverable transaction but have distinct journal paths. Current repair receipts preserve original manifests. No automatic application-folder migration exists: `migrate` creates a new scaffold plus a legacy inventory rather than repairing an existing application in place.

Current generators declare explicit project artifacts for standard Node/Python/Go backends, GenAI backends and selected Functions workers, optional frontend, database, containers, environment examples and documentation. Those declarations identify current targets, not historical layout versions or permission to replace production code. Existing setup/assessment integrations and compatibility inventories provide the native-agent and exact-ownership prior art.

## Goals / Non-Goals

**Goals:** Give a terminal developer and a supported agent the same truthful repair capabilities and next actions; make reviewed application-file patches and exact locked private verification preparation executable without granting an LLM direct writes to the real project; independently version repair guarantees, recipes and documents; preserve legacy recovery and histories.

**Non-Goals:** Guess arbitrary source mappings, replace source with starters, install agents or global tools, enable governance, advance activation, regenerate/upgrade dependency locks, change dependencies just because templates advanced, execute provider/state migration, publish Git changes, or reinterpret old provenance as current proof. Local application verification is scoped evidence, not a guarantee about all behavior or live conformance.

## Decisions

### One contract, explicitly distinct recipes and documents

Introduce repair contract 1 as the first explicitly recorded contract. Keep the existing Azure transformation semantics as recipe `azure-local-layout`, version 1, with exact flat-root/recognizable-partial source identities and the independent-root target inventory. Add recipe `application-layout-patch`, version 1, for explicitly mapped project-file patches, not automatic legacy detection. Its target identity is the current generated application artifact inventory (layout ID/version, workload selection, exact logical names/portable paths and inventory digest). Source identity is the observed recorded/developer-declared inventory; do not retroactively label arbitrary legacy code as a historical generated layout.

Current preview and report schemas become 2. New history receipts and repair journals become schema 2; update journal schema 1 is unchanged. Application inventory, patch input, preparation policy/results, verification receipts and private-workspace records each have explicit independent schemas. Extend the first unreleased schema/contract definitions coherently; do not retag published release or activation identity. Optional preparation is explicit and absent preparation means none, never inherited authority. CLI version, repair contract, complete recipe/layout/provider identity, protected inputs/effects, exact verification/preparation/toolchain/package sources, clocks and scope participate in approval fingerprints. Different CLI/contract/recipe/layout/schema/validation or changed source/staging/destinations/tool identity requires a fresh preview.

Old schema-1 previews are deliberately non-executable. Old schema-1 history remains byte-identical and historical. Exact old sealed repair journals can recover their recorded writes only; current schema-2 repair journals require a supported contract/recipe identity before recovery. Recovery compatibility is explicit and independent from new-plan eligibility; an unknown future identity blocks without modifying the journal. Never normalize old identities in place.

### Separate inspection, staged patch review, verification, and commit

Provide `liftoff repair --capabilities --json` without needing a project. Provide `liftoff repair <project> --inspect-layout --json` for bounded application inventory. Ordinary repair and `--check` inspect the local Azure scope unless an application patch is explicitly selected; neither silently widens an infrastructure approval. Check is always non-executing. Ordinary bare repair on genuine interactive input and stderr TTYs displays one immutable proposed plan and offers a default-No Yes/No approval instead of asking the developer to copy its fingerprint.

Application workflow:

1. Inspect the selected project and current target inventory. Record source digests, modes, directory inventory, known provenance, unsupported/excluded paths, and reference-review limitations. The agent reads actual source and resolves every intended mapping, including custom files.
2. Author replacement files and a schema-1 patch document in an explicitly selected staging directory outside the project. Each operation maps one exact observed source to one exact target (same path for a reference edit); moves require absent destinations. Bind the inspection digest, expected source digest/mode, current target identity, reference disposition and exact verification commands. No recursive folder move or wildcard ownership exists.
3. Run `liftoff repair <project> --application-patch <patch.json>` for the normal interactive journey, or add `--check --json` for non-executing inspection. The CLI validates the document and staged bytes, protects manifest/configuration/framework/managed/history/state/secret boundaries, checks collisions and complete mappings, and creates an external preview without executing project code. An explicitly requested preparation preview also performs the bounded installed-tool identity probes described below; pure capabilities and application inventory do not.
4. In the interactive journey, display the exact staged checks, optional preparation commands/package sources, suppressed lifecycle policy and host-effects warning. Separately ask default-No consent for project-code execution, any dependency preparation, and declared network effects; obtain every required consent before any preparation/check command. A broad file-repair Yes does not supply these permissions. Create a registered private candidate and cache from the bounded inspected files, apply only the proposed bytes there, run exact frozen preparation if approved, then bounded exact checks. The CLI does not initialize real backends, install global tools, publish Git, regenerate locks or transfer dependencies/build outputs back. Staging is not an OS or network sandbox: trusted verifier/dependency code can affect the host and network, and unsupported mandatory-isolation requirements block. Explicit automation can instead use `--verify-plan <fingerprint>` with separate preparation and declared-network permissions.
5. Only after fresh successful staged verification, ask a separate default-No question to apply the displayed exact file changes. A Yes binds the already displayed internal fingerprint; no ordinary hash-copy step exists. Reload and rebind project and staged inputs under the project lock, retain private original-byte backups and immutable historical descriptors, then use the existing confined repair transaction. Automation can equivalently use `--approve-plan <fingerprint>` without weakening any gate. Never execute the patch by direct agent writes to the application first.
6. Read back actual committed effects. Report inventory/proposed/verified/committed states and remaining local/activation work distinctly. Verification proves only the declared checks. Interrupted writes use `--recover`; a post-commit behavior issue requires a new reviewed patch or user-controlled version-history recovery, never blind rollback.

The alternative of prose-only guidance followed by direct application edits was rejected because retrospective preview would not constrain writes. A generic template-driven mover was rejected because neither legacy versions nor arbitrary reference semantics are reliably known.

### Registered locked dependency preparation

Preparation is an optional explicit part of the staged application patch, not a new generic installer. Resolve it against the candidate's exact post-patch component manifests and lockfiles and the selected current target identities. Bind their bytes/modes, provider ID/version, declared commands, compatible installed tools, credential-free package sources, lifecycle/network policies and private output roles into the same preview and verification digest. Missing, mismatched, changed or unselected inputs block; no lock generation, update, fallback dependency resolution or reuse of an old unprepared receipt is permitted.

| Registered lane | Required candidate inputs and existing tools | Permitted private effects and limits |
| --- | --- | --- |
| `npm-ci` v1 | Selected Node backend or frontend `package.json` plus `package-lock.json`; compatible installed Node and npm | Exact `npm ci` with lifecycle scripts disabled and audit/fund/config side effects suppressed; frozen dependency tree and a fresh private cache; no original/global installation |
| `uv-locked-sync` v1 | Python `pyproject.toml` plus `uv.lock`; compatible installed Python and uv | Locked sync into a fresh private environment; no Python downloads, source builds or project-install/build hooks; unavailable wheels or required unsupported hooks block |
| `go-mod-download` v1 | Go `go.mod` plus `go.sum`; compatible installed Go | Exact module download/read-only checks with private module/build caches and local toolchain only; no module/checksum updates or automatic toolchain download |

The supported inputs are concrete current generated layouts, including the actual Go checksum artifact. Reject unsupported workspace, local/VCS, authenticated or escaping package-source arrangements rather than infer authority. Package sources are explicitly registered credential-free sources; project/global package-manager configuration, tokens, credential helpers, hooks, live `node_modules` and `.venv` are not copied or inherited. Show download/install and possible code/host effects before consent. Lifecycle/build hooks stay suppressed; if a project needs unsupported enabling, report a blocker rather than secretly weakening suppression.

Resolve trusted installed executable and interpreter paths using existing tool-resolution/compatibility facilities, excluding project/staging PATH shims. Bind canonical resolved launcher/interpreter identity and version/requirements, not version text alone. Run only bounded metadata probes, in a sanitized environment and non-project/non-staging working directory; no project scripts or package installation runs during preview. Recheck identity before effects. Missing/incompatible tools are precise blockers, never repair authority to install a global tool. Qualification-only missing tools can be restored explicitly to an isolated test location without changing product behavior or the original machine configuration.

Protect the copied candidate inputs and compare exact source/manifest/lock bytes, modes and directory inventory after each preparation and check. Permit only the declared private dependency/cache/build-output roles. No changed protected candidate, failed preparation/check, stale tool identity or incomplete cleanup can issue a successful verification receipt. Offline/private-cache misses remain causal blockers, with no silent network fallback. A preparation grant alone does not authorize project checks, lifecycle execution, real-project writes or any global effects.

Qualify actual generated Node backend build and existing tests after preparation, plus optional Vue frontend preparation/build and tests only if the selected project declares them. The generated frontend has no test script, so build-only evidence must remain build-only. Exercise the registered Python and Go positive/negative lanes with compatible tools and real libraries where available; report missing uv or other unavailable native lanes rather than count mocks or dependency-free Node tests as framework qualification.

### Registered private-workspace cleanup and recovery

Before private preparation/check effects, persist a project-bound external record of the CLI-created workspace's canonical path, creation identity, declared disposable roles, plan/provider/tool/input bindings and owner/progress information. This record is distinct from user patch staging, source backups, immutable history, project transactions and successful verification receipts. Update progress through registered bounded records; no directory-prefix guessing or arbitrary caller-selected cleanup root is allowed.

Normal completion cleans the disposable workspace. Incomplete cleanup or interruption preserves recovery metadata and the real effects already performed. Explicit `liftoff repair <project> --recover` can clean only the exact externally authenticated/registered CLI-created workspace identity for that project after safe owner/confinement checks. Refuse links/junctions, identity changes, active or uncertain owners and unsupported records; a bare PID or expiry does not prove cleanup safety. Never delete user patch staging, a live project, global caches, original-byte backups or history, and never rerun a verifier or restore source through private cleanup. Preserve records on incomplete cleanup. Existing sealed project-journal recovery remains a separate unchanged authority.

### Managed process-tree settlement on Windows via stock Job Objects

A single hash-bound Windows controller source asset (`assets/repair/windows-job-controller.ps1`) is hosted by stock Windows PowerShell 5.1 / .NET. It enforces normal system policy with `-NoProfile -NonInteractive` without `-ExecutionPolicy Bypass`, `-EncodedCommand`, or inline script evasion. The Windows client default `Restricted` policy, inherited process-scope `PSExecutionPolicyPreference`, `ConstrainedLanguage`, AppLocker/WDAC, `AllSigned`, or outer job constraints are explicit causal admission blockers that fail closed before target creation. Demonstrated policy rejection is distinguished from generic controller, compilation, launch, or admission failure; a policy blocker is never inferred from an arbitrary exit code. The controller-host execution context is kept strictly separate from untrusted target/preparation environment variables: inherited restrictive process policies are not relaxed or dropped, weaker policies are not set, and project-provided environment overrides cannot alter host policy or inherit arbitrary profile/module hooks.

1. **Atomic Job Membership**: The controller creates an unnamed non-inheritable Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` and no breakaway flags (`JOB_OBJECT_LIMIT_BREAKAWAY_OK` / `JOB_OBJECT_LIMIT_SILENT_BREAKAWAY_OK`). Scope and membership checks verify assignment against the exact private Job handle, not whether a process is in any arbitrary job. The root process is bound atomically during `CreateProcessW` using `STARTUPINFOEX` with `PROC_THREAD_ATTRIBUTE_JOB_LIST` and `CREATE_SUSPENDED`. Membership is verified before `ResumeThread`. `HANDLE_LIST` is restricted to intended stdio handles only—never job, control, or startup handles. If admission fails, no target code starts; any allocated suspended root is terminated/unwound. No start-then-assign fallback is permitted.
2. **Channel Separation & State Differentiation**: Untrusted target stdout/stderr are kept strictly isolated as bounded/redacted streams; project stdout cannot forge control evidence. An authenticated private local control pipe, cryptographic 64-character hex startup nonce (not present in target argv/env/stdio), length-prefixed JSON control protocol, sequence numbers, and bound invocation/workspace/controller IDs are used. The lifecycle explicitly distinguishes: known unsupported/policy rejection before requested `CreateProcess`; failed creation with definitive no-target evidence; allocated-but-still-suspended admission failure requiring owned-handle unwind; and resumed execution with possible effects (never labeled 'nothing started').
3. **Kernel Settlement Evidence**: Root process exit only records its status. Settlement requires `QueryInformationJobObject` `ActiveProcesses == 0` while the controller holds the job, including inherited child processes. An empty probe job or unadmitted/unbound response is never successful settlement. Abort/timeout/output-limit uses `TerminateJobObject` on the job handle and waits for zero active processes. Controller loss, crash, channel closure, or accounting uncertainty stays unknown/retained; `KILL_ON_JOB_CLOSE` is a safety backstop, not assumed proof. Parent disconnect signals the controller to terminate its job.
4. **Managed Scope & Verified Literal Argv**: Scope is precisely the Job's assigned root and inherited members. Explicitly NOT whole-host proof or an OS/network sandbox; WMI/service-created or escaped processes are not claimed managed. Uses verified literal Win32 command line encoding (with native argument-echo tests for empty args, embedded quotes, trailing backslashes, Unicode, and metacharacters for supported Node/Python/Go lowering) and canonical UTF-16LE null-separated environment block encoding; no `cmd.exe` shell expansion, batch lowering, or string interpolation.
5. **Testing & Installed-Package Qualification**: Admission failure before spawn, restrictive process-scope policy, target-env policy override attempts, root exit with live descendant vs settled control, literal argument preservation, spoofed stdout rejection, abort/timeout/output limits, controller failure handling, and no success receipt on uncertainty. Installed-package tests must exercise the packaged asset and its pinned digest/host identity, not CWD or source fallback. All native Windows support and evidence remains an open gate until actual execution in a dedicated branch-only CI checkpoint.

### Interactive consent binds the displayed plan without hash entry

Reuse the existing exact-plan approval helper's usable stdin/stderr TTY checks, strict true response, default No and recognized cancellation handling, adding action-specific prompt wording while preserving update's default wording and behavior. Repair's caller disables prompts for check, JSON, non-TTY, absent/ended streams and other read-only modes. Explicit exact execution flags remain available in JSON/non-TTY mode; piped yes, generic flags and formatting never supply authority.

Revalidate the same preview after consent, before preparation/checks and under the mutation lock; do not silently rebuild or expand it after a Yes. Changed inputs, locks, staging, directory inventory, tool identity or stale verification require a new displayed review. Keep prompts on stderr and JSON on stdout. A decline, cancellation or EOF before any effect consent leaves the project unchanged. After separately approved preparation or verification has run, a later decline prevents further unapproved CLI mutations and file commit, but must report earlier preparation/verifier/host effects rather than promise that nothing happened.

### Bounded inventory and explicit safety exclusions

Reuse the real current generator's project declarations to publish target identities, never starter bytes as replacement candidates. Use native path resolution and existing confinement/snapshot utilities. Enforce finite file/count/byte/depth budgets, reject unsafe links/case aliases, and expose incomplete coverage instead of silently ignoring it. No Git clean filters, hooks, scripts, provider calls, state reads or installs are part of inspection.

Inventory actual application/configuration/test/container/script/CI/documentation paths and exact literal/relative reference locations without returning source snippets or environment values. Reference discovery is explicitly incomplete for dynamic resolution; the patch's reviewed reference inventory and real checks must address remaining uncertainty. Exclude VCS internals, Liftoff records, framework/agent control data, infrastructure/state, credentials, live dotenv files, dependency/cache/output trees and unsafe files. Exclusions are read/write restrictions, not ownership inferred from a prefix. Supported customizations are individually declared files with exact before/after bindings; unknown target identities or unresolved mappings remain blocked.

### Thin native integrations with exact additive ownership

Append `liftoff-repair-copilot`, `liftoff-repair-claude`, and `liftoff-repair-codex` to exact managed inventories. Use `.github/prompts/liftoff-repair.prompt.md`, `.claude/commands/liftoff-repair.md`, and `.agents/skills/liftoff-repair/SKILL.md`. Reuse the selected-agent native surfaces rather than inventing shell aliases. Generate repair integrations even with governance `none`; that does not render policy/setup/assessment or enable activation.

The same body negotiates supported repair capabilities, including the registered preparation matrix when requested, follows its structured actions, and manages the staged application-patch review. It teaches normal interactive repair without hash copying and separately explains preparation, lifecycle suppression, project-code, network and file permissions. Native agents can use exact automation flags internally only after equivalent distinct developer approvals, without asking the developer to type the fingerprints. It is versioned by its managed hash, not skill SemVer. Older complete inventories remain readable and expose the new exact files as additive reviewed drift. Unowned differing collisions remain protected under force; existing managed conflict rules still apply. Preserve unrelated neighboring skills and old history.

### Project-targeted terminal and JSON guidance

Schema-2 reports include current identity/capabilities and structured next actions with executable, argument array, working directory, scope, authority, and human explanation. Render shell text using the existing POSIX/PowerShell formatter, never hand-concatenated commands. Repair paths stay positional; governance/update keep their registered syntax. Human labels explain local baseline verification instead of surfacing raw `seed-verified` as a remedy.

Always state that bare interactive repair previews and asks, check is read-only, JSON/non-TTY cannot implicitly execute, and exact approval writes. Disclose the bounded installed-tool probes used only by explicit preparation previews. Live metadata, preparation, lifecycle/project-code/network effects, file mutation and recovery are distinct scopes. Human next actions prioritize rerunning the normal interactive command; fingerprints remain audit/automation data, not mandatory copy/paste instructions. Offer native repair invocation only for selected agent surfaces, with a safe update check if missing. Setup continues after repair through update and local status/verify/resume; assessment remains read-only and never executes its remediation.

## Risks / Trade-offs

- Dynamic imports and custom build systems cannot be completely inferred -> return bounded observations and unresolved coverage; require explicit reference review and real project checks instead of claiming generic conformance.
- Project verification commands can have side effects -> independent exact consent, optional explicit declared-network consent, isolated working copy, bounded execution and honest non-sandbox disclosure; file approval alone runs none.
- New strict schemas invalidate old approvals -> give a fresh same-project preview remedy, preserve old history, and retain only explicitly compatible sealed recovery.
- Native filesystem/shell behavior varies -> use portable path parts, platform formatting and collision checks; wire new cases into Windows CI and report unrun native qualification honestly.
- Source may contain sensitive data -> exclude state/credential/env inputs, avoid content in public reports, and keep original-byte backups private rather than embedding application bytes in repository history.
- Locked dependencies may need unavailable native wheels, hooks, authenticated feeds or tools -> publish exact provider limitations and causal blockers; never relax locks, inherit credentials or invent successful preparation.
- Private cleanup can be interrupted or its owner uncertain -> retain authenticated creation/progress records and refuse unsafe cleanup instead of deleting by PID, age or directory prefix.
- Windows client default Restricted policy, process policy or AppLocker blocks controller script -> report causal admission blocker; do not bypass policy or use encoded commands.
- Descendants in process tree can outlive root process -> kernel Job Object tracks ActiveProcesses and terminates on command; uncertainty retains workspace without claiming success.

## Migration Plan

Generate new integrations for new selected-agent projects. Existing supported projects use ordinary reviewed update for exact managed additions; no manifest, policy or activation version bump is required. Existing infrastructure users use the intentionally changed interactive bare repair or a non-executing schema-2 check; exact automation flags remain compatible. Interrupted schema-1 repairs recover under the explicit legacy mapping. Application users inventory first, stage a concrete patch, separately approve verification/network/file effects through readable prompts, then resume local setup. No release version/ref changes or OpenSpec archival are part of this change.
