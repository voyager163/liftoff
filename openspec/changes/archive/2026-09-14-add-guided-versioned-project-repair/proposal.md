## Why

Existing projects can preview and approve a bounded Azure infrastructure repair, but developers lack a native repair skill, a practical path for reviewing broader application layouts, and an explicit compatibility contract for repair records. Terminal guidance must connect these surfaces without turning previews, agent reasoning, or old receipts into write authority.

## What Changes

- Generate a thin native `liftoff-repair` integration for every selected supported coding agent, including projects with governance disabled. Keep Copilot/Claude native `/liftoff-repair` and Codex `$liftoff-repair` equivalent, explicitly owned, safely installed by reviewed update, and separate from setup and assessment.
- Add a read-only repair capabilities interface and actionable, project-targeted human/JSON guidance for check, preview, approval, blocked/partial results, recovery, and resumed local setup.
- Intentionally change ordinary bare repair on genuine interactive input/output TTYs to show its immutable proposed effects and ask an action-specific Yes/No question, default No, before applying that exact plan. Developers do not copy or type fingerprints in the normal journey; internal fingerprint binding and optional explicit automation interfaces remain. Changed inputs or stale verification invalidate the displayed plan instead of rebuilding it after consent.
- Add bounded application-layout inspection with explicit current generated artifact targets, recorded source provenance, file digests, reference locations, exclusions, and unresolved decisions. It is a real inspection capability, not an automatic application migration recipe.
- Add an independently identified, reviewed application-patch lane: the agent authors exact file mappings and replacement bytes in external staging, the CLI binds before/after bytes, modes, directory inventory, references and verification to an expiring fingerprint, and only the confined transaction applies the separately approved patch. Unknown mappings remain blocked.
- Teach the repair integration to use that inspection to review the actual project's imports, customization, build/tests, containers, scripts, CI, and documentation. Separately explain and authorize staged project-code execution, declared network effects and file mutation through clear action-specific prompts, without mandatory hash-copy steps; preserve rollback/history without rewriting Liftoff provenance or activation proof.
- Add opt-in, separately reviewed dependency preparation for the private disposable verification environment from exact staged manifests and lockfiles. Bind installed compatible toolchains, registered package-manager commands, package sources, lifecycle policy and effects into approval/verification identity. No original-project or global installation/configuration changes, copied live dependency trees, ambient credentials, lock regeneration/upgrades or committed dependency/build output are authorized.
- Qualify real generated Node backend build/tests and optional frontend build after locked preparation and before exact patch commit. Publish a concrete npm/Python/Go support matrix, with causal blockers for missing tools/locks, unsupported sources or required lifecycle/build hooks. Suppress lifecycle hooks by default rather than silently enabling them. Dependency-free checks do not establish framework-preparation coverage.
- Retain bounded private preparation/verification cleanup and recovery records and recheck source, locks, modes and directory inventory after prompts, preparation and checks. Preparation, declared network/lifecycle/code effects and file mutation remain independently consented; staging is not an OS/network sandbox and earlier effects must be reported after later cancellation.
- Add a Windows managed process-tree settlement controller using stock Windows PowerShell 5.1 / .NET hosting a single hash-bound packaged controller source asset with genuine Win32 Job Objects. Settlement is proven precisely for the assigned root and inherited Job members, never as whole-host or sandbox guarantees. Client-default `Restricted` execution policy, inherited process-scope `PSExecutionPolicyPreference`, `ConstrainedLanguage`, AppLocker/WDAC, `AllSigned`, or outer job constraints are explicit causal admission blockers that fail closed before target creation; demonstrated policy rejection is distinguished from generic controller/compile/launch/admission failure and cannot be inferred from an arbitrary exit code. The effective host and process-scope policy is retained without project-environment overrides, and no automatic policy changes, execution policy bypasses, inline `-Command`, or `-EncodedCommand` evasion are used.
- Introduce independent `repairContractVersion`, recipe ID/version and supported source/target layout identities. Evolve approval previews, reports, history and repair journals with explicit document schemas and compatibility rules.
- **BREAKING**: replace schema-1 current repair reports and approval previews with schema-2 documents. Old previews cannot authorize execution. Preserve old history unchanged and support only explicitly recognized, externally sealed interrupted-journal recovery.
- Preserve `--check` as non-executing and bare JSON/non-TTY repair as preview-only; JSON/non-TTY execution requires an exact explicit execution flag. No, cancellation, EOF, redirected input or a generic yes flag cannot authorize writes. Cancellation reports any earlier separately authorized verification/external effects instead of claiming nothing happened. Retain `--approve-plan <fingerprint>` and explicit verification fingerprints only as optional automation/backward-compatible interfaces. Do not add force/yes bypasses, agent installation, automatic generic folder moves, stateful public execution, release changes, or activation-version changes.

## Capabilities

### New Capabilities

None; this extends existing repair, ownership, CLI, and guidance contracts.

### Modified Capabilities

- `liftoff-project-repair`: independent repair identities and document compatibility, read-only application-layout inspection, exact locked private dependency preparation, and a bounded reviewed agent-assisted application journey.
- `liftoff-cli-workflow`: executable repair capabilities/inspection/preparation modes and schema-2 project-targeted next actions with truthful independent approval and recovery boundaries.
- `liftoff-template-ownership`: exact selected-agent repair identities, safe additive managed installation, and protection of application/provenance/history boundaries.
- `liftoff-repository-governance-profile`: equivalent native repair handoffs alongside setup and assessment without enabling governance or expanding activation authority.
- `liftoff-user-documentation`: native skill access, precise preparation/tool/lock support, supported and unsupported layout journeys, terminal recovery, and independent repair version/bump rules.

## Impact

Affected areas are `src/application/repair`, CLI registration/output, the sealed filesystem transaction and private verification-workspace lifecycle, a single hash-bound packaged Windows Job controller source asset under `assets/repair/`, generated agent integrations and their exact ownership/manifest compatibility inventories, packaged documentation, package smoke, and focused cross-platform/framework tests. Reuse existing generators, installed-tool constraints, stock Windows PowerShell 5.1 / .NET hosting on Windows without bypasses, project boundaries, shell formatting, hashing, and external receipt storage; no new runtime dependency is planned.

The CLI package remains at 0.12.2. The existing activation identity (0.12.0, manifest 7, policy 6, activation 3, graph schema 2, state/evidence/approval schemas 3, compatibility schema 4) and historical records remain unchanged. No live resources, release refs, dependent workspaces, or publication are in scope.
