## MODIFIED Requirements

### Requirement: Infrastructure execution requires lane-specific eligibility
Repair SHALL distinguish verified-undeployed, stateful and unknown scope from executable eligibility. Local infrastructure transformation requires authoritative current undeployed proof. In this release, pre-existing Azure deployment/state adoption, relocation, partition or address migration SHALL remain publicly planning-only even when private primitives exist. Internal qualified state operations retain their separate protection/approval requirements and do not become public through a generic approval.

#### Scenario: Complete scoped absence is independently observed
- **WHEN** every required supported state/resource binding has fresh authoritative absence evidence
- **THEN** local repair can become eligible subject to exact approval and apply-time recheck

#### Scenario: No local state file exists
- **WHEN** remote ownership is unobserved
- **THEN** missing local state leaves eligibility unknown and plan-only

#### Scenario: Existing state or resources are found
- **WHEN** pre-existing deployed state or resources are observed
- **THEN** the public result identifies deferred stateful planning and does not expose an executable import/migration remedy

#### Scenario: State appears after preview
- **WHEN** the reviewed scope changes or cannot be re-observed
- **THEN** infrastructure writes stop before mutation

### Requirement: Repair discovery separates metadata from sensitive state inspection
Live repair metadata requires explicit scope and existing permissions. Public reports SHALL remain payload-free, and the first-release existing-deployment path SHALL not read state contents or expose state-read/write execution flags. Any retained private state inspection capability SHALL require its own exact authority and protected workspace; it SHALL not become enabled by local repair, assessment or adoption. Discovery SHALL not register providers, enroll credentials, initialize backends or mutate resources.

#### Scenario: Live discovery is not requested
- **WHEN** ordinary repair encounters an unresolved remote binding
- **THEN** it reports the missing observation without a provider request

#### Scenario: Provider access is denied
- **WHEN** a scoped read is denied or incomplete
- **THEN** the result remains unknown rather than absent

#### Scenario: Discovery succeeds
- **WHEN** metadata observations complete
- **THEN** scope/provenance/freshness are reported without raw sensitive payloads or activation completion

#### Scenario: State contents are needed to establish address mappings
- **WHEN** existing-deployment mapping requires a sensitive state read
- **THEN** the public CLI identifies the deferred boundary rather than performing that read or inventing a command

### Requirement: Agent repair is additive and framework-owned
Additive agent repair SHALL preserve existing selections and applicable Spec Kit default. For OpenSpec/Spec Kit it SHALL use pinned official staged integration operations; for Manual it SHALL install only explicitly selected Liftoff-native integrations without an external framework. Desired-state/manifest changes SHALL be limited to exact approved selection fields and observed output. Workflow switching uses its separate reviewed operation, and agent removal or metadata-only installation claims SHALL not be performed by this lane.

#### Scenario: Add Codex to an existing project
- **WHEN** a supported additive request is approved
- **THEN** real applicable native integrations are installed while existing agents and unrelated files survive

#### Scenario: Choose Codex as Spec Kit default
- **WHEN** an explicit approved default change selects Codex
- **THEN** official framework state and metadata agree without uninstalling other agents

#### Scenario: Stateful infrastructure is unrelated to agent addition
- **WHEN** agent work is independently eligible but infrastructure is plan-only
- **THEN** only the approved agent scope can execute and the infrastructure limitation remains visible

#### Scenario: Agent-only repair completes while other local work remains
- **WHEN** scoped integration checks pass
- **THEN** requested agent repair can complete without claiming application-wide readiness

#### Scenario: A requested agent is recorded but its integration is missing
- **WHEN** supported native output is missing for an already selected agent
- **THEN** preview identifies actual repair rather than using the agent list as installation proof
- **AND** unknown framework history or missing project seeds are not fabricated

### Requirement: Supported stateful recipes preserve every resource binding
Retained internal stateful recipe contracts SHALL preserve every resource binding, require complete mappings and reject unapproved create/update/delete/replace effects. They SHALL not be advertised as publicly enabled pre-existing Azure state migration in this release. New-environment activation can use only its separately qualified, exactly owned bootstrap/handover scope, not arbitrary existing state.

#### Scenario: Refactor a resource into a shared module
- **WHEN** an explicitly qualified internal recipe is exercised
- **THEN** it must preserve live identity rather than accept replacement as migration
- **AND** its existence does not enable a public existing-deployment command

#### Scenario: Partition state across environment roots
- **WHEN** a retained internal partition contract is validated
- **THEN** each instance requires exactly one verified destination or preserved source disposition

#### Scenario: A plan introduces a resource replacement
- **WHEN** protected planning detects an effect outside approved state-only purpose
- **THEN** execution remains blocked and no local approval overrides it

### Requirement: Application layout inspection reports actual bounded evidence
Repair inventory SHALL report actual project files, provenance, digests/modes, explicit compatible active bindings, target artifact identities, reference locations, exclusions and unresolved scope. A supported compatible layout SHALL not require canonical-folder relocation solely because new templates differ. Missing mappings remain unresolved. Inventory SHALL remain bounded, read-only, project-confined and script/network/state/secret-free across supported platforms.

#### Scenario: A customized backend lives in a legacy folder
- **WHEN** a supported explicit binding establishes compatible current paths
- **THEN** inventory preserves that layout and proposes moves only for an actual standard violation
- **AND** unsupported mappings are not guessed from generation hashes

#### Scenario: Layout inspection is incomplete
- **WHEN** limits, unsafe links or unknown references prevent complete observation
- **THEN** dependent patches remain blocked with the exact limitation

## ADDED Requirements

### Requirement: Preserved-layout repairs publish bindings through a separate reviewed operation
An application patch SHALL retain its existing prohibition on writing provenance/control files. If verified file moves require updated active bindings, a separately registered exact metadata operation SHALL preserve original provenance, bind the committed patch receipt and current bytes, and publish only approved bindings. Failed publication SHALL remain explicit partial progress and shall not fabricate historical generation or activation proof.

#### Scenario: Verified source move changes an active binding
- **WHEN** the approved patch commits but binding publication cannot safely complete
- **THEN** the CLI reports committed files and incomplete binding work separately
- **AND** ordinary update cannot guess the missing provenance or repeat the move

#### Scenario: Windows destination changes after verification
- **WHEN** the source, destination or junction/case identity changes before application
- **THEN** the exact plan is rejected on Windows, macOS and Linux and concurrent files are preserved
