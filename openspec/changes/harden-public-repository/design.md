## Goals / Non-Goals

**Goals:** Make source-repository checks and publication enforceable with one maintainer; distinguish configured, executed, passed, and enforced states; bind security evidence to real code, dependency graphs, and artifact digests; make activation reversible only through explicit, bounded operator action with readback. Make user/contributor onboarding, reporting and support boundaries discoverable and consistent in both the source checkout and distributed documentation.

**Non-Goals:** A vulnerability audit in this planning task; another application release system; native migration; deployed-product governance; cloud or organization provisioning; stronger paid/preview features as prerequisites; zero-trust protection against the repository owner deliberately rewriting hosted policy; corporate CLAs/DCOs, relicensing, support SLAs, new chat/forum infrastructure or badge certification. Review by the sole maintainer is the authority boundary, not a second-person approval gate.

## Decisions

### 1. Repository-scoped desired state and staged evidence

Use checked-in desired-state data and read-only diff/readback commands for source-repository settings, separate from packaged generated-project policy. If repository configuration is added, `.github/github-app.yml` must follow GitHub's documented schema; do not invent a parallel app configuration schema. Security inventories and evidence contracts can live under explicitly named `security/` files. Runtime evidence should be sanitized, bounded, and retained as CI/release evidence rather than committed secret-bearing responses.

A control record distinguishes `available`, `configured`, `executed`, `passed`, `enforced`, `unavailable`, `inapplicable`, and `blocked`, with observation time, repository/ref/SHA, desired-policy digest, tool/config identity, check run, and readback. These states are not interchangeable. Required unavailable controls block the applicable activation phase; optional unavailable capabilities remain visible limitations.

Reject copying organization rules, teams, licensed features, or the generated governance activation engine into this source-repository task. Repository admin access can still edit rules; removal of bypass does not remove that administrative fact.

### 2. PR-only branches without single-maintainer deadlock

Target `develop` and `main` explicitly. Require PRs, zero approving reviews, no CODEOWNERS or last-push approval, resolved conversations, strict current-head checks, no bypass actors including admin exemptions, no force pushes, and no deletions. Preserve `main` linear history and compatible squash/rebase merging. Do not expand to `release/*` or `hotfix/*` without an observed need and explicit policy; generated-profile ref requirements do not automatically apply here.

Do not use a branch `restrict updates` rule with an empty bypass list: it would stop valid merges. No initial required signing of contributor commits, merge queue, deployment prerequisite, or environment reviewers. Keep existing classic protections until equivalent-or-stronger replacement behavior is proven and read back. Do not temporarily remove the Windows requirement to make activation pass.

Ordinary maintainer PR merge remains the single authority decision. Disable blind auto-merge for the hardening/control-plane path; bot-generated dependency/security fixes are proposals, not approvals.

### 3. Treat check policy as a control plane, not just an App name

Register exact check context plus producing App and applicability after real runs. An Actions App-bound status prevents another App from satisfying that context, but does not bind the check to a workflow file, workflow revision, scanner invocation, or trusted policy.

Maintain an explicit control-plane inventory covering workflow files, actions/reusable workflows, security inventories and scanners, report parsers/aggregators, scanner configuration and query packs, exception policy, dependency/release scripts, desired hosted settings, and publisher definitions. Compare both file content and inventory membership using trusted base-policy data. Candidate policy deletion, severity weakening, parser substitution, skip filters, and publisher permission changes receive a clear report for the sole maintainer before merge. Candidate exceptions or scanner suppression are not automatically authoritative for judging their own PR.

Use trusted base-policy evaluators where practical; separate candidate execution from policy evaluation. Never run candidate scripts in a privileged evaluator or execute downloaded reports. Ordinary same-App checks alone cannot cryptographically attest unchanged workflows on a user-owned repository. Document that residual boundary, keep maintainer merge authority, and prove deliberate policy tampering is visible; do not claim an unavailable organization-required-workflow feature.

#### Distinct policy-only maintenance admission

Finding assessment and PR admission are separate decisions. Finding assessment always reports the actual results under adopted trusted policy; proposed exception/disposition data never turns that result clean. Normal PR admission requires successful complete analysis and passing applicable finding policy. A distinct policy-only maintenance decision can make a narrowly qualified proposal mergeable while its existing base findings remain honestly reported. This resolves the adoption cycle without a separate pre-merge authorization command, receipt or reviewer gate.

The trusted-base validator, not a candidate label, owner string or requested mode, derives eligibility from the exact base/head trees and registered policy-data paths. A maintenance proposal may modify only explicitly allowlisted exception/disposition data already registered by the base. Source, dependency manifests/locks, workflows, scanners, rules/query packs, evaluator code, inventories, thresholds, permissions and publisher definitions must remain unchanged. Unknown paths, file-type/mode changes, symlinks, renames or unapproved configuration changes are not maintenance eligibility; code-changing PRs follow normal admission and cannot use this route to pre-authorize new findings.

Complete, compatible base/candidate observations must prove no new raw findings or unassessed surfaces. Every new or expanded exception/disposition must match an actually observed trusted-base finding and satisfy the existing exact-scope, rationale, evidence, owner and validity-window rules. Do not create unused future exceptions or weaken stale-entry rejection. Exact withdrawals and stale-entry cleanup may reduce permissions but cannot create a grant. A renewal needs fresh valid scoped evidence; expiration is not automatically extended. Existing policy finding/expiry diagnostics remain visible and are distinct from a scanner, parser, provenance or coverage failure, which always blocks admission.

Confirmed unremediated credential exposures are never eligible for maintenance admission. An exact pending false-positive/nonfunctional-fixture proposal must retain the unresolved finding until adoption, be supported by its scoped evidence, and must not downgrade a known confirmed exposure. Incident/remediation evidence cannot be erased or fabricated through policy maintenance. This path does not replace the separately authorized credential-owner remediation process.

Use a distinct required security-admission result alongside mandatory analysis-completion, integrity and existing functional checks. Normal mode consumes the actual finding verdicts; maintenance mode reports only proposal eligibility, with the unchanged findings and unadopted policy diff visible. Standalone audit/finding results keep their real outcomes; do not post synthetic green statuses or use broad `continue-on-error`, `neutral` or skipped checks to disguise them. Do not simultaneously require an unconditional clean finding result for this same maintenance path, recreating the cycle, and do not weaken existing functional checks or bypass native hosted rules to make it work. Qualify the actual required-check composition before changing hosted settings.

Bind admission evidence to repository, current base/head, the complete changed-file set, proposed policy bytes/digest, trusted validator/policy identity and compatible analysis evidence. Drift, new commits, unavailable coverage, incomplete dependency snapshots or unknown severity invalidate the decision. A claim in the candidate that it was approved is not proof. Active-policy authority is derived from independently loaded adopted base content and its verified source context; any approval/evidence-reference fields are traceability data rather than candidate-issued authority.

Keep comparison identity separate from provenance identity. A policy-only edit necessarily changes commit and whole-tree identities; unchanged findings are compared through exact stable protected-source/graph inputs, detector/rule/configuration and normalized location or component/chain identity. Exclude only the explicitly admitted policy-data change from protected-input comparison, never arbitrary source or unrecognized fields. Preserve and validate each actual commit/run identity independently; finding equivalence neither permits stale evidence nor requires base/head SHAs to be equal.

The sole maintainer's ordinary merge is the adoption decision; no blind auto-merge is allowed for these proposals. Subsequent normal PR and release assessments reload the newly adopted policy and reassess their exact revisions. A normal code fix may withdraw an exact now-inapplicable waiver only when complete evidence proves the finding resolved and the effective permission set is no broader than the trusted base; remaining stale entries and new/expanded candidate grants still fail normal validation. This permits fixes to retire obsolete exceptions without creating another adoption cycle.

Maintenance eligibility is not a clean scan, an adopted exception or release qualification. A maintenance-admission report can never be consumed as publication evidence. Newly introduced code findings must be fixed or remain blocked; this mechanism does not establish a future-finding approval workflow. Initial policy registration, executable control-plane changes, malformed/unverifiable state and exceptional incident recovery do not silently acquire a maintenance bypass.

### 4. Least-privilege Actions and trust-separated execution

Repository defaults remain read-only and bot PR approval disabled. Enumerate the used/approved action repositories and full immutable references; use selected-action settings and SHA enforcement when available plus a deterministic repository policy check. Validate local/reusable/transitive action references too, documenting any platform limitation rather than treating a pinned outer action as proof of immutable internals. Do not introduce a mutable SLSA generator just for a badge.

Validation runs on ephemeral GitHub-hosted runners. Fork and Dependabot PRs receive no repository secrets, publishing credentials, cloud access, environment authority, or `id-token: write`. Preserve `first_time_contributors` approval as the execution boundary; do not silently add merge/deploy approvals. Disable persisted checkout credentials where not specifically needed. Grant `security-events: write` only to the narrow CodeQL reporting path where supported; test GitHub's PR upload behavior without increasing fork privileges or using privileged fallback workflows.

No untrusted checkout or artifact execution under `pull_request_target` or privileged `workflow_run`. PR concurrency cancels superseded runs but cancellation never passes the required gate; publication serializes by release identity without cancelling an in-progress publish. Bound every job and subprocess and report timeout/error states.

Partition caches by trust, source/lock/tool identity, and purpose. Do not restore PR-writable caches or accept PR-built artifacts as executable privileged release inputs. Reports/artifacts carry run, attempt, event, ref, SHA, inventory/policy/tool identity and digest; enforce producer/origin, completeness, schema, size and path checks. Release rebuild/qualification uses an approved protected commit on a fresh runner. A filename or matching workflow name is not artifact provenance.

OSV is narrowly assigned to non-npm complete dependency graphs, not npm, IaC or images already assigned above. Verify pinned-version extractor coverage before accepting it.

### 6. Successful analysis and finding policy are separate gates

Use advanced CodeQL, not default setup, with explicit supported languages for source and materialized projects. Require successful analysis for every applicable category AND evaluate findings. Prefer native repository code-scanning merge protection for supported source findings plus an explicit fail-closed source result gate. The latter covers required findings outside PR diff locations and verifies complete current-source results, not only successful upload. Its actual verdict remains unchanged during decision 3's separate maintenance-admission evaluation.

GitHub documents that native merge protection excludes merge-queue groups and Dependabot PRs analyzed by default setup, and requires alert locations in the PR diff. This plan uses no merge queue and must prove advanced-setup Dependabot/fork paths. Generated paths are not necessarily in a committed PR diff: the required generated-output finding gate evaluates actual local reports directly regardless of GitHub annotations/upload visibility. A tool exit of zero, successful SARIF upload, empty parser output, or absent analysis category is not a clean bill of health.

New gates block high/critical vulnerabilities and explicitly enumerated policy violations. For CodeQL distinguish security severity from reliability severity; define query/rule mappings. Checkov rules without comparable severity are governed by the reviewed blocking rule-ID list. Unknown/malformed severity or report schemas produce an error needing triage. Do not equate non-security warnings with vulnerabilities or discard unmapped security findings.

Retain the current stricter npm rule: every unresolved npm advisory needs an exact valid exception, including moderate/low findings. Other lower-severity findings remain visible with an owner and triage record, not automatically ignored. New exception schemas reuse the existing discipline but scope finding identity to tool/rule, graph or generated case, package/version and reviewed chains, or exact artifact digest/location as appropriate. Include rationale, mitigation, owner, review date and expiry; high/critical maximum 30 days, lower maximum 90 days; no automatic renewal, broad glob ignore, blanket `ignore-unfixed`, stale exception, cross-graph transplant, or suppression of infrastructure failure.

Credential exposure follows decision 7 rather than vulnerability-severity thresholds or the 30/90-day exception windows. An untriaged secret detection or confirmed unremediated exposure cannot be temporarily accepted as an ordinary dependency finding. Decision 3 may qualify an exact policy-only false-positive proposal for an existing base detection, but does not resolve that detection before adoption or admit a confirmed unremediated exposure.

Run dedicated PR live checks in addition to deterministic fixture-based ordinary tests. Dependency diffs help PR triage but do not replace full current-graph checks. Schedule full scans weekly on applicable protected refs and rerun full security qualification for releases; scheduled failures create actionable maintainer triage and block subsequent publication until a fresh passing qualification, without rewriting history or synthesizing PR results. Live databases/outages can change security results; ordinary unit tests remain deterministic. Reports record database/query versions and times; release evidence must be from that release attempt, no older than 24 hours, and unexpired at publication, or be refreshed.

### 7. Free native features with honest capability limits

Preserve secret scanning, push protection, private vulnerability reporting, Dependency Graph, Dependabot alerts/security updates. Use Dependency Review for supported changed graphs and advanced CodeQL/Copilot Autofix where available to this public personal repository. Autofix remains a suggestion reviewed and tested like any other change, never automatic approval.

Read capability/entitlement state before proposing a setting. Generic/non-provider patterns, partner validity/extended metadata, AI generic detection, and AI Scan are not assumed free personal-repository switches; paid/preview features are excluded from the default. Do not fetch or publish secret values for acceptance. Use safe provider-supported dummy/test fixtures only where permitted, with no live credential or harmful payload.

#### Secrets coverage and evidence

Inventory the current committed source and the published repository branches/tags whose reachable history is in scope, binding names to exact commit identities and observation time. Include tracked documentation, configuration and workflow files, not only application code. Distinguish that declared repository scope from unreachable/deleted objects, other people's complete fork histories, external copies and unsupported content types; never claim those were scanned without evidence. An initial assessment and subsequent full-scope assessments need completion/coverage records for the declared scope. Incoming PR validation must inspect the candidate tree and newly introduced commits, including a credential added and removed before the final PR revision. A clean final tree alone is insufficient.

Use GitHub-native scan metadata where it establishes actual scope and completion, not merely feature enablement or an empty alert list. Evidence includes detector/configuration identity where available, refs/revisions, observation and completion times, inspected surfaces, skipped/unavailable coverage, sanitized finding counts and disposition. If native APIs cannot expose sufficient metadata without retrieving secret values, require a bounded owner-supplied sanitized record or qualify the explicitly allowed local scanner for that gap; do not fetch raw secret-bearing alert responses as a workaround or invent missing provider guarantees.

For a demonstrated gap in history assessment or fork-safe merge enforcement, run a pinned Gitleaks version locally in the authorized isolated scan workspace or unprivileged CI job. Inspect only the declared repository content and complete required Git objects, not developer homes or unrelated worktrees. Reconcile fetched ref identities and history completeness before scanning; shallow clones, missing refs/objects, scanner errors and incomplete reports remain blocking. Separate current-content and history coverage explicitly, and verify every skip/exclusion against trusted base policy. Preserve native GitHub scanning and push protection rather than replacing them.

Gitleaks configuration, rules, exclusions and report adapters are control-plane inputs evaluated against trusted base policy; a code-changing PR cannot allowlist its own detector hit or disable its gate. The decision 3 maintenance route changes only exact registered disposition data for existing base detections, never detector rules or an active finding verdict before adoption. Require full redaction and bounded metadata-only output at the scanner boundary for stdout, stderr, reports and error paths, with deterministic leakage tests before real assessment. Do not persist raw matches, source excerpts or credential values in logs, PR comments, artifacts or committed baselines. Scanning reads the explicitly authorized repository content locally; it introduces no external secret-validation service or upload of content/findings. Missing safe evidence blocks qualification instead of prompting a paid service, privilege escalation or silent alternate tool.

#### Alert disposition and remediation

Every detection needs an owner-bound, sanitized disposition: unresolved, confirmed exposure awaiting remediation, exact reviewed false positive/nonfunctional fixture, or remediated exposure with evidence. Use provider alert IDs or nonsecret location/rule/commit identifiers, never secret values as identifiers. Untriaged detections and confirmed unremediated exposures block secrets-protection acceptance and applicable intake/publication gates regardless of a generic severity label.

Confirmed exposures require the credential owner to revoke or rotate the credential under separate explicit authority, remove it from current source where present, and provide sanitized remediation evidence. Deleting a file, deleting a branch, rewriting history or closing an alert alone does not establish invalidation. Historical occurrences of a remediated credential may be recorded precisely without mandatory history rewriting. A false-positive or nonfunctional-fixture disposition must be exact, justified and reviewed through trusted policy; no broad baseline suppression, live-credential exception or automatic dismissal is permitted. These records are distinct from the existing 30/90-day vulnerability exceptions. Do not test discovered credentials against an issuer or rotate them as a side effect of scanning.

#### Push, fork and bypass qualification

Qualify native push rejection independently from scan detection and PR merge blocking. After separate authorization for hosted tests, use only permitted provider-supported nonfunctional fixtures on exact disposable refs with publication disabled. Record the actual detector response, actor/ref/policy identity and whether the push was rejected. A fixture that the provider does not recognize is inconclusive, not proof of prevention; never mint or use a live credential to force a test to pass.

Inspect effective bypass permissions and available bypass reporting, distinguishing repository push protection, user-level protection and any licensed delegated-bypass controls. Record actors/roles, limitations and the outcome of any explicitly authorized safe bypass test without silently changing access or introducing another reviewer. Branch-rule bypass configuration does not establish secret-protection bypass policy.

Separately exercise fork PRs and same-repository proposals against the receiving protected branch. Do not assume target-repository push protection blocks a push to someone else's fork or prevents that PR from merging. Where native controls cannot enforce the boundary, the qualified unprivileged Gitleaks result must block ordinary intake of the supported detection on the exact candidate; absent or skipped execution cannot pass. Qualify decision 3's data-only maintenance path separately without clearing its existing finding result, permitting new detections or waiving confirmed exposures. Prove positive and negative behavior under actual authorized actor/event paths, and label simulations honestly. An observed route that bypasses the required admission rules, or an unavailable safe proof, remains an explicit blocker for that claimed protection.

Document that local Git commits are outside repository push enforcement and that no detector proves the absence of every possible secret. Record supported patterns, unsupported surfaces, false-negative limitations and distinctions between detection, push rejection, merge denial and remediation. Periodic full-scope assessment and changed-configuration requalification keep the initial evidence from becoming an indefinite clean certificate.

Dependabot currently covers four npm directories and Actions. Add supported Python `uv` and Go update entries after confirming exact ecosystem behavior; retain default-branch targeting, supported-stack ownership and runtime-major discipline. Provider/image updates still follow reviewed supported-stack refresh. Unsupported automation is reported while real scanning remains required.

### 8. Extend npm publication with qualified immutable bytes

Keep `.github/workflows/release.yml` as the coordinator and reuse package checks, smoke tests, identity validation, npm dist-tag selection, trusted publishing/provenance and canonical post-publication verification. Split qualification/build from narrowly privileged publishing. Publication accepts only an explicitly selected protected `main` commit, with all required qualification evidence, unchanged policy and exact version identity; arbitrary manual refs and unqualified tag pushes cannot publish.

Pack once, inspect/install/scan that exact tarball, hash it, and publish that same tarball rather than implicitly repacking the source. Compare canonical npm integrity with the qualified tarball in addition to existing version/dist-tag/install checks. A fresh privileged job validates producer/run/ref/attempt/digests and uploads/publishes bytes without executing package scripts from transferred artifacts. Inventory all expected assets before publishing; qualification artifacts from PR runs never qualify a release. In particular, a maintenance-admission result is not a finding verdict or publication receipt: after adoption, a new release attempt must evaluate the actual source/artifacts against the adopted policy and satisfy all release requirements.

Use an exact publisher environment/ref policy with zero required reviewers and OIDC for npm where supported. Move `id-token: write`, `contents: write` and attestation rights to the smallest required jobs. Hosted trusted-publisher registration and environment/ref support must be read back and tested before activation; their existence is not proven by workflow text.

Tag authority is an implementation prerequisite, not an assumption. Define two independently targeted `v*` policies: a creation restriction with only a verified publisher exception, and an update/deletion restriction with no bypass, including for that publisher. Ordinary branch rules have no exception. Resolve and test the real publisher actor against repository-level rules before application. The shared GitHub Actions App is not a workflow-specific identity: it is acceptable only with evidence that nonpublisher jobs/events/refs cannot obtain equivalent tag authority. If that cannot be proven, stop tag-control activation and present a repository-only dedicated GitHub App enrollment proposal for explicit owner authorization; do not grant broad PAT access, install an App, or weaken restrictions silently. Lack of a feasible authorized identity remains an honest release-hardening blocker, not a claimed scoped publisher.

Coordinate qualification, creation of the exact tag, draft release assembly, npm publication, canonical verification and final GitHub Release publication explicitly in the existing workflow. Do not rely on a `GITHUB_TOKEN`-created tag causing another push-triggered workflow; use explicit job/reusable-workflow or dispatch coordination for the same exact commit and avoid duplicate release runs. Separate the tag-creation exception from publisher ability to move/delete tags.

Enable immutable future GitHub Releases only in the authorized hosted phase. Assemble every expected asset/checksum/SBOM/provenance/security summary on a draft first, verify the complete asset set and digest binding, then publish. Read back the immutable state and protected tag. Historic releases are not retroactively immutable; GitHub title/notes remain editable and release-deletion semantics are not overstated. A partial npm/GitHub failure is reported precisely; never unpublish, overwrite assets, move tags, or automatically roll back protections. A retry may reuse only already-published identical bytes and exact version identity; otherwise publish a corrected new version after review.

An SBOM identifies components; vulnerability assessment evaluates those components against a database; provenance identifies production; signing/notarization establishes platform-specific trust. None alone proves secure bytes or SLSA L3.

### 9. Native modernization is a separately owned interface

This hardening change owns source controls and the current npm release qualification contract. A separately authorized native-modernization change owns bundle creation, installer/update behavior, platform support, native signing and notarization, and any distribution-contract change. It must provide explicit platform/architecture and component inventories, embedded runtime versions, exact artifact digests, reproducible build/qualification identities, SBOMs, vulnerability results, signing/notarization status and verifiable provenance to the same publisher boundary.

Do not scan a pretend native container, claim native qualification, copy the former candidate, or remove npm publication. If native modernization lands before implementation, re-read its merged specs and reconcile this change through an explicit plan revision before modifying release behavior.

### 10. Evidence-driven acceptance instead of badges

Maintain an acceptance matrix mapping each normative scenario to deterministic policy tests, actual scanner execution, hosted behavioral proof, or readback. Logical roles distinguish successful source analysis, actual source/dependency/secrets/generated finding reports, policy integrity, security admission and existing functional CI. Normal admission consumes passing applicable findings; maintenance admission uses only the bounded decision 3 contract without converting finding reports to success. Hosted contexts and their required-versus-reporting composition are recorded only after actual runs.

Positive and deliberately failing cases use exact unmerged refs and benign vulnerable/insecure fixtures; never merge the negative fixture or include real credentials. Capture PR head and tested merge/base SHA, workflow commit, App ID, job/category, run/attempt, policy/tool identities, time and conclusion. Prove every proposed required context can turn red. Include missing reports, scanner outage, unsupported language, skipped/cancelled jobs, unauthorized suppression, changed workflow, artifact tampering, fork/Dependabot events, and wrong publisher ref/identity. Prove merge/tag restrictions only after separate authorization for hosted test effects; do not mutate global settings just to produce planning evidence.

Secrets acceptance additionally needs declared source/history completion, sanitized disposition/remediation records, safe native push-rejection evidence, fork/same-repository merge-gate evidence, and effective bypass readback. Test added-then-removed PR content, incomplete history, exclusion tampering and redaction/error paths. Mocked detector results or configuration readback alone cannot satisfy these behavioral requirements; missing evidence is reported against its specific protection.

Maintenance admission additionally needs positive exact-data proposals and negative mixed-code/rule/workflow edits, new findings, future/stale exception grants, confirmed exposures, incomplete snapshots, forged candidate approval metadata and stale base/head/policy evidence. Prove that standalone finding results remain blocking before adoption, ordinary code fixes can safely withdraw resolved waivers, and a release rejects maintenance evidence. Keep local simulations separate from separately authorized real PR/merge qualification.

Destructive-rule probes must use explicitly authorized disposable refs with equivalent rule payloads, not attempt deletion, force pushing or tag movement on real protected branches or releases. Record payload equivalence and read back exact production target patterns separately; report this distinction instead of claiming a destructive production test. Reserve test identities, disable publication for them, and agree on cleanup/retention before creating refs that deletion rules may intentionally retain.

## Risks / Trade-offs

- Live advisory outages and new disclosures can block merge/release -> Dedicated security lanes, explicit infrastructure diagnostics, bounded retry and fresh rerun; never fail open or turn mutable security data into ordinary-test fixtures.
- Existing Windows/freshness failures can delay adoption -> Record exact failing evidence and separately remediate/requalify; retain protections and avoid importing modernization fixes blindly.
- Full generated language/image coverage costs runner time -> Explicit equivalence/coverage matrix, trust-separated caches and concurrency; missing coverage is a blocker, not a silent path filter.
- Same-App check names do not protect workflow content -> Trusted base-policy comparison plus sole-maintainer control-plane review; document limits rather than claiming unavailable organization enforcement.
- An exception PR can be blocked by the finding it seeks to disposition -> Distinct exact-data maintenance admission, honest unchanged finding reports and ordinary maintainer merge as adoption; no candidate-issued authority or general bypass.
- Maintenance classification could swallow code or new findings -> Base-derived exact path/type and input-identity guards, complete comparison evidence, normal-mode fallback and negative qualification; uncertainty blocks rather than broadens eligibility.
- Shared publisher identity may not be narrow enough -> Prove token/ref/job boundaries before activation; halt for an explicitly authorized dedicated identity if needed.
- Personal-repository feature/API availability can differ from docs -> Readback and behavioral proof; preserve visible gaps and prohibit unapproved paid/org substitutes.
- Secret evidence can itself disclose credentials -> Redact at the local scanner boundary, retain only sanitized metadata, test failure paths and avoid raw hosted alert responses.
- Push protection may not cover fork submissions or every pattern -> Qualify push and merge paths separately, use Gitleaks only for the approved demonstrated gap, and leave unproven claims blocked.
- A historical credential can remain usable after source deletion -> Require owner-authorized revocation/rotation evidence; neither history rewriting nor an alert dismissal substitutes for remediation.
- Draft/npm/GitHub publication is not atomic -> Exact-byte idempotency, precise partial-state records and forward fixes; no destructive rollback.
- Linux-only image execution leaves other architecture evidence incomplete -> Declare tested platforms and require actual additional image/component qualification before claiming those targets.
- Owner can alter hosted policy -> No normal bypass, drift reporting and explicit recovery records; this design does not promise protection from a malicious repository owner.
- Corporate benchmark policies can impose unsuitable legal or support obligations -> Reuse original information architecture and routing patterns while preserving GPL terms, one maintainer and best-effort support.
- A private conduct contact is not yet approved -> Require owner-supplied publication consent and a usable route before publishing the revised policy; never invent a contact or repurpose vulnerability intake.
- Shortening docs can discard critical safety detail or break packaged links -> Move rather than delete contracts, preserve navigation and verify explicit links/routes against both checkout and extracted tarball.

## Migration Plan

1. **Inventory only:** Refresh baseline/ref/settings and existing checks; record capability gaps, existing protections, CI blockers, trusted-publisher feasibility, supported generated coverage, declared secrets-scan refs/surfaces, effective bypass visibility, documentation/intake routes and the owner-supplied conduct-contact prerequisite. Planning revisions do not execute scans or hosted tests.
2. **Implement through PRs:** Introduce inventories, deterministic policy tests, genuine security producers, release qualification and the bounded README/contribution/community improvements using existing mechanisms. Keep hosted changes disabled; do not bundle baseline remediation without evidence and scoped review or describe planned controls as already enforced.
3. **Qualify unmerged candidates:** After authorization to run CI and any hosted tests, exercise positive and safe negative cases on exact unmerged refs, including fork/Dependabot, secrets push/merge boundaries and all existing OS checks. Establish source/history scan completion and sanitized remediation status without retrieving hosted secret values, using real credentials or implicitly authorizing revocation/rotation. No real publish/sign/deploy side effects. Recheck final approved workflow/policy identities after merging their implementation.
4. **Prepare hosted change:** Produce exact before/after settings, App/context bindings, publisher proof, applicability, API capability results and recovery instructions. Re-read drift immediately before applying. Obtain separate explicit permission for this global repository operation.
5. **Activate incrementally:** Preserve classic protections while adding equivalent-or-stronger rules, selected actions/SHA policy, CodeQL finding protection and verified publisher/environment/tag/immutable-release controls. Require readback plus permitted behavioral proof before retiring superseded protections. Apply twice safely without destructive replacement.
6. **Operate and recover:** Retain scheduled scans/drift checks, owner-visible failures and current support/security/conduct destinations. On failed readback or lockout stop further changes; preserve before/after evidence. Any emergency administrative edit is narrowly scoped, separately authorized, logged, expires where applicable, and is requalified. No blanket weakening, permanent admin bypass, or automatic rollback of controls.

Exact action/tool versions, platform-supported policy fields and publisher App IDs are resolved during implementation qualification, not invented here. A capability or publisher feasibility failure keeps its phase blocked under these same contracts; resolving it does not grant new effects automatically.
