## Why

Liftoff's public source repository has useful release verification and dependency auditing, but its current hosted controls do not consistently require reviewed pull-request paths, successful security analysis, or finding-based protection. Harden the actual `develop` baseline without closing public participation, requiring a second maintainer, or confusing generated-project governance with controls enforced on Liftoff itself. Make public onboarding, contribution expectations and reporting routes equally explicit so newcomers can use and contribute to the project without navigating maintainer-only procedures or assuming corporate support.

## What Changes

- Preserve the public, standalone, GPL-3.0-only repository, contribution and fork access, existing history, and the working `@msn-control/liftoff` npm distribution. The verified planning base is `70d10881b46d873118d825735696f39b6d35ebe0`, not the separate native-modernization candidate.
- Refresh `README.md` as a first-use landing page with a clear supported install/example, separate terminal and coding-agent steps, and discoverable workload, privacy, support, contribution and release guidance. Move detailed repair/migration material behind maintained links without deleting safety or compatibility information or presenting planned controls as active.
- Make `CONTRIBUTING.md` a proportionate newcomer path, link advanced maintainer operations separately, and add lightweight bug/feature intake and a PR checklist. Keep public questions, bugs and features distinct from private vulnerabilities and owner-approved private conduct reporting. Preserve the single-maintainer model and contribution licensing; do not import corporate CLAs, mandatory DCOs, support SLAs, contacts or new community services.
- Make documentation completion verifiable in both the repository and the exact npm artifact: consistent links, reporting routes, branch/support facts, README length rules and packaged community documents. Preserve useful existing release notes and privacy guidance rather than adding duplicate policy documents or unsupported quality badges.
- Require pull requests into `develop` and `main`, zero approving reviewers, resolved conversations, and real App-bound checks; prohibit ordinary branch bypasses, force pushes, and deletion. Preserve existing `main` protections during migration rather than locking all updates.
- Harden Actions with selected actions and immutable full-SHA references, read-only defaults, no bot approvals, bounded execution, and isolated secret-free fork validation. Treat workflows, scanner policy, exceptions, and publisher definitions as a control plane requiring explicit sole-maintainer scrutiny, not blind auto-merge.
- Provide a distinct, trusted policy-only maintenance admission path for exact exception/disposition data addressing findings already observed on the trusted base. Source, dependencies, workflows, detector rules and evaluators stay unchanged; findings remain honestly reported and confirmed unremediated credential exposures cannot be waived. The maintainer's ordinary merge adopts valid policy without a separate pre-merge approval step. This path neither pre-authorizes new findings in code-changing PRs nor supplies release qualification.
- Make secrets protection an evidence-backed acceptance requirement: establish current-source and declared Git-history scan coverage, review sanitized alert outcomes, require credential-owner remediation of confirmed exposures through separately authorized revocation/rotation, and qualify push blocking and fork/merge behavior with safe nonfunctional fixtures. Record effective bypass permissions and detection limitations. Missing coverage or enforcement evidence prevents a claim of completed secrets protection; this is not a guarantee that every local commit or arbitrary secret can be prevented.
- Add advanced CodeQL successful-analysis checks and finding-based protection, plus explicit source and generated-output finding gates. Materialize supported generated projects to analyze actual Python, Node.js, Go, OpenTofu, Docker configuration, and built images rather than assuming TypeScript strings are covered.
- Extend existing npm audit and exception mechanisms, which already cover root, telemetry service, Node backend, and frontend graphs. Cover Python standard/GenAI locks and Go dependencies explicitly; distinguish dependency review, complete current graphs, and update automation. Preserve deterministic ordinary tests while adding dedicated live PR, scheduled, and release security validation.
- Use free, applicable GitHub-native security capabilities first, Checkov for IaC and Trivy for actual images, and a narrowly justified non-npm graph scanner where native tooling leaves an enforcement gap. Block high/critical vulnerabilities and defined policy violations in normal change/release qualification; preserve the existing stricter npm exception contract. A qualified maintenance-admission result never changes a blocking finding into a clean scan. Never interpret missing analysis, unavailable tooling, or unreadable reports as clean.
- Extend the current npm release pipeline with exact-source and artifact-digest qualification, scoped publication, separately protected tag creation and mutation, complete draft-first immutable future GitHub Releases, SBOMs, provenance, and fresh vulnerability evidence. Prove publisher identity feasibility before activating restrictions. Record a future native-distribution interface without implementing or assuming that migration.
- Roll out in stages: read-only inventory, implementation through approved PRs, positive and safe negative proofs on exact unmerged refs, then separately authorized hosted settings application and readback. The present planning workflow creates or revises planning artifacts only.

## Capabilities

### New Capabilities

- `liftoff-repository-security-validation`: Source-repository Actions trust boundaries, source/generated security coverage, secrets-scan and enforcement qualification, precise result and exception policy, distinct policy-only maintenance admission, and evidence-backed check qualification.

### Modified Capabilities

- `liftoff-source-repository`: Add single-maintainer hosted protection, control-plane ownership, secrets-protection readiness, public onboarding and contribution/reporting contracts, capability reporting, and staged activation requirements without changing public-source ownership or generated-project governance.
- `liftoff-template-dependency-security`: Extend isolated live npm auditing to PR and release security lanes while retaining scheduled/manual auditing, exact exceptions, four-graph coverage, and deterministic ordinary tests.
- `liftoff-npm-distribution`: Add qualified artifact publication, scoped publisher/tag authority, future release immutability, packaged community-document/link acceptance, and a bounded native-modernization handoff while preserving all existing npm installation and publication requirements.

## Impact

Implementation will affect repository workflows, explicit security inventories and policies, audit/release scripts, focused tests, dependency automation, `README.md`, contributor/security/conduct/developer/release guidance, issue/PR templates, and the packaged documentation surface. A private conduct destination must be supplied and approved by the owner before that revised policy is published; no contact is invented or copied from a reference project. Hosted Actions settings, security features, repository rulesets/protection, publisher environment/identity, and immutable-release settings are a later, separately authorized repository-scoped phase, not effects of creating or approving these artifacts.

No application feature, packaged governance-profile activation, cloud provisioning, deployed-service probing, telemetry-production administration, organization control, paid/preview service, repository transfer, history rewrite, relicensing, corporate contribution agreement, support guarantee, or native-distribution migration is included. Existing Windows CI and freshness failures are evidence to reconcile before enforcement, not permission to weaken checks or perform remediation during planning. No commit, push, PR, scan, CI dispatch, signing, or publication is authorized by this planning work.
